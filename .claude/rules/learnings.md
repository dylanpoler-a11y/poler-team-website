Append-only `[FAIL]` / `[WIN]` / `[FAST]` log, split out of this project's `CLAUDE.md` (its Learnings section points here) to keep that file lean. One dated line per entry, newest at the bottom. Read before structural changes; add an entry on every bug fix, non-obvious success, or faster path found.

- 2026-07-03 [FAIL]: MCP `create_lead` posts `firstName/lastName/country/notes/assignedTo` to `/api/save-lead`, which expected `first/last/countryIso` — names+country silently dropped (9 nameless leads). Fixed server-side in save-lead.js (accepts both shapes) so both MCPs are covered; when adding an MCP tool that proxies an existing endpoint, diff the tool schema against the endpoint's destructured body field-by-field.
- 2026-07-03 [FAIL]: The Listings nav tab never opened — the sidebar click dispatcher in crm.js had a branch for every action EXCEPT `listings` (switchView existed, was just never called). When adding a nav item, grep the dispatcher for its data-action.
- 2026-07-13 [FAIL]: `api/agent/search-properties.js` PROPERTY_TYPE_ALIAS lacked the CRM's own Alert Property Types vocabulary — `propertyType=Single Family` passed through as a PropertySubType Bridge doesn't know → count 0, no error, and every Sammy drip/blast/button send for SFH-typed leads silently sent nothing. Added 'single family'/'multi family' aliases; keep in sync with `lib/alert-search.js` TYPE_MAP (email alerts already mapped it — only this endpoint was blind).
- 2026-07-16 [FAIL→fix]: "Flash didn't set a reminder" was a CRM-PANEL STALENESS bug, not a Flash bug — Flash's server DID create the no-answer retry reminder ~7s after the call (correct note + 10 AM ET). But `crm.js` rendered a lead's reminders from the page-load `allReminders` cache (`populatePanel`→`renderLeadReminders`) and NEVER re-fetched on panel open, so a reminder created after the tab loaded was invisible → Kevin re-added it by hand (Julian Niño ended up with 3 duplicate next-day Call reminders). Fix: `populatePanel` now fires `loadReminders()` then re-renders on open (instant cache paint first, no flicker); `handleFlashMessage` always refreshes reminders after a coached call (was gated on a well-formed `data.reminder`, so dead-lead calls with `followUp:null` never refreshed the panel). RULE: any panel showing rows another system mutates out-of-band (reminders, notes) must RE-FETCH on open, never render only the load-time cache — the 3rd "Flash didn't do X" false alarm traced to the panel not auto-refreshing.
- 2026-08-04 [FAIL→fix]: "Dead leads don't grey out" — the styling WAS applied (`renderTable()` re-runs after every panel save) but was invisible: the row template set `opacity:.45;color:#94a3b8` INLINE ON THE `<tr>`, and almost every cell carries `.td-muted`/similar setting its own `color` — a class on the td beats a color inherited from the tr, so only the opacity landed, fading already-grey text by a hair. Fix: `<tr class="lead-dead">` + a real rule in crm.css drawing a continuous strikethrough as a **td background-image linear-gradient** (transparent → 2px line at 50% → transparent) rather than `text-decoration`, so ONE unbroken line crosses the whole row instead of striking each cell's text separately (breaks only behind the avatar/status-badge, which have their own backgrounds — reads intentional). RULE: to restyle a table row, style the TDs; anything inherited from the tr loses to any class on the cell. Verified on a standalone harness against the real crm.css (CRM itself is login-gated).
- 2026-08-04 [FAIL]: contact-sync `phoneKey()` = `digits.slice(-10)`, so it dedupes on the last 10 digits and IGNORES the country code — `+57 7875056901` and `+1 7875056901` collide. Edwin Caraballo signed up twice off the same ad: the 7/23 record carried a bogus +57 prefix (signup form prepends the SELECTED country's dial code onto a number the user typed in full — 787 is Puerto Rico), that WRONG number was pushed to Kevin's iPhone, and when the 8/3 record arrived with the CORRECT +1 it was skipped `dup-phone`. Net: the phone keeps the first-seen, possibly-malformed number forever and the corrected one never syncs. Fix direction: key on full E.164 (or on national digits + country) and, on collision, prefer/repair to the newer better-formed number instead of always keeping the first.
- 2026-08-04 [FAIL→fix]: "Eduardo Vera got the test alert by email but not WhatsApp" — NOT a code path failure: his number is US (+1 786…), and Meta blocks Marketing-category WhatsApp templates to US numbers (the documented 7/15 63049 constraint). The REAL bug: `sendWhatsappAlert` treated Twilio's synchronous 201 "queued" as `status:'sent'` — 63049 only materializes ASYNC on delivery — so the CRM showed "WhatsApp ✓ sent" for messages that never arrive, and the UI's own 63049 explanation string could never fire on this path (Twilio log: Eduardo's test + Jul 22 + Jul 29 weeklies all undelivered/63049 while reported sent). Fix: US pre-check at the TOP of sendWhatsappAlert (`/^1\d{10}$/` on digits of lead.phone) returns `status:'error'` with a reason containing "63049" BEFORE link generation or the Twilio POST — all 3 consumers (weekly cron best-effort, send-test-alert, send-map-props) inherit it, and both crm.js renderers match /63049/ so the "keep US leads on Email" message now actually shows. Verified live on the Test Check lead (temporarily +1/whatsapp-only): 502 "No channel delivered" with the US reason, zero Twilio messages created; lead restored after. RULE: any API whose failures are ASYNC (Twilio→Meta, email bounces) must pre-check known-deterministic rejects synchronously, or the UI reports success for guaranteed failures.
- 2026-08-05 [FAIL→fix]: YASSER LENIS round 2 — "sigo recibiendo viejitas" DESPITE the 7/23 precon profile rebuild. TWO senders, only one honored the profile: the weekly alert applied the Preconstruction feature (MLS New/UC units), but the SAMMY DRIP (`whatsapp-lead-monitor/build2-properties.js buildSearchParams`) reads only the FLAT alert fields (cities/price/beds/types) and can't see features — they live ONLY in the Alert Profiles JSON wrapper — so drip #2 (8/4) sent a 2007 Downtown resale condo. Fix 2 (Kevin's actual definition): "preconstruction" = the CURATED /preconstruction TOWERS (payment plans, entrega 2027-2030), not MLS units — `lib/alert-search.js searchPreconTowers()` now returns towers as Bridge-shaped pseudo-listings (`ListingId PRECON:<id>`, `PreconTower:true`, `PreconUrl`) prepended per-profile, with a stable rank sort (fresh towers → fresh MLS → sent towers → sent MLS; shuffle still varies within rank) so MLS New/UC serves as backfill once the ~41-tower pool exhausts under weekly no-repeat. Renderers branch on PreconTower: email "Desde $X"/"Entrega YYYY"/no MLS# (BOTH duplicated builders — send-alerts.js AND send-test-alert.js — keep in sync), WhatsApp label "Preconstrucción NAME, AREA — desde $X (entrega YYYY)" and skips share-property (towers link to `/preconstruction?building=<id>` — new deep-link param, page clears it on any filter touch; api already had id=). GOTCHA: send-test-alert does NOT log 'Alert Sent' activity — after manually sending the 5 towers, seed the dedupe row via log_lead_activity or the next-day cron re-sends the identical set. RULE: any lead-facing preference stored ONLY in the profiles wrapper is invisible to every consumer that reads flat fields — when adding a wrapper-level flag, grep ALL property-senders (weekly cron, test, map-send, Sammy drip, arrival blast, buybox) for flat-field readers.
- 2026-08-06 [FAIL→fix]: JOSÉ BENDAYAN repeats ROUND 2 — the 7/15 no-repeat fix was correct but its MEMORY WAS NEVER WRITTEN: only ONE 'Alert Sent' row existed in the whole Lead Activity table (my manual 7/15 seed). Root cause: all three Lead Activity writers (send-alerts.js logActivity, send-map-props.js logMapSendActivity, log-activity.js) included `'Lead Record ID': [leadId]` — a field the table does NOT have — so Airtable 422'd (UNKNOWN_FIELD_NAME) the ENTIRE record, and the best-effort `catch {}` swallowed it. Every send "succeeded", zero rows landed, getSentListingIds always returned just the seed → recycling resumed. The endpoint even returned `{success:true}` for writes that never landed (MCP log_lead_activity for Yasser 8/5 = also lost; re-seeded). Diagnosis path that nailed it in 4 calls: count target-table rows (1) → probe a direct write WITHOUT the suspect field (200) → probe WITH it (422 UNKNOWN_FIELD_NAME) → grep all writers for the field name. Fixes: dropped the field from all 3 writers (rows are keyed by Lead Email — the reader queries only that), failures now console.error (visible in Vercel logs) instead of silent, José re-seeded with his 16 VIEWED MLS ids via the DEPLOYED endpoint (proving the fix live; next-send sim = 311 fresh / 5 picks, 0 repeats). NOTE: Reminders table has its own working 'Lead Record ID' TEXT field — those writers are fine; do not "fix" them. SIDE FINDING not yet fixed: ALL Lead Activity writes (Call rows too) stopped ~2026-07-01 and Conversations-table writes 422 on 'Timestamp' — separate breakages, same silent-swallow class. RULE: a fire-and-forget write path MUST at minimum log non-2xx responses, and any "success" a caller reports must be verified against the store once after deploy — Airtable rejects the WHOLE record on one unknown field, so a single stale field name = 100% data loss that looks like success.
